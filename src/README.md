# КТ2. Подготовка и запуск производственной партии

Процедурная консольная версия: только функции и стандартные структуры данных.
Собственных классов, dataclass, NamedTuple, Enum, глобальных изменяемых данных и подключения СУБД нет.
Используются json, argparse, pathlib, datetime и copy из стандартной библиотеки.
Требуется Python 3.10 или новее. Устанавливать внешние библиотеки не нужно.

## Запуск

Распакуйте архив, откройте терминал в папке src:

```bash
python main.py
python main.py --scenario shortage
python main.py --scenario busy
python main.py --scenario quality_rejected
python main.py --scenario ready --save result.json
```

На Windows при необходимости используйте `py -3` вместо `python`.
Входной demo_data.json находится относительно main.py, поэтому запуск возможен также из другой рабочей папки.
Для собственного набора данных: `python main.py --data another_data.json`.
Каждый запуск читает исходные данные заново. Исходный файл не изменяется.
Функции, меняющие состояние, возвращают копию набора данных; функции расчёта возвращают результаты.

## Данные и логическая модель

Все идентификаторы в примере — целые числа. Даты представлены ISO-строками,
отсутствующая фактическая дата — null. Это формат обмена JSON, а не физическая модель СУБД.
Имена полей соответствуют ER-модели, пробелы в именах заменены подчёркиваниями.

| Коллекция JSON | Сущность модели | Ключ |
|---|---|---|
| products | Изделие | id_изделия |
| materials | Материал | id_материала |
| specifications | Спецификация изделия | id_изделия + id_материала |
| equipment | Оборудование | id_оборудования |
| employees | Сотрудник | id_сотрудника |
| batches | Производственная партия | id_партии |
| batch_equipment | Оборудование партии | id_партии + id_оборудования |
| delays | Факт переноса | id_переноса |
| control_protocols | Протокол контроля | id_протокола |

Все девять коллекций представлены, включая изначально пустую историю переносов.
Почта, пароли и telegram_id не добавлены. Ответственный задаётся при регистрации партии.
Набор данных должен соблюдать ключи модели: уникальные PK и пары составных PK, существующие FK.
Демонстрационные нормы расхода условные, не являются технологическими нормативами.

Потребности, отчёт о дефиците и предложение оборудования — временные результаты функций,
а не дополнительные сохраняемые сущности.

## Автоматизируемые операции

| Задача BPMN | Функция |
|---|---|
| Зарегистрировать производственное задание | register_batch |
| Рассчитать потребность | calculate_material_requirements |
| Проверить наличие материалов | check_material_availability |
| Подобрать доступное оборудование для операций партии | select_equipment |
| Зафиксировать запуск и статус партии | record_batch_launch |

Дополнительно реализованы assign_equipment, add_control_protocol и record_delay.
Они сохраняют подтверждённые назначения, результаты контроля и причины переноса.
Проверку документации, качества, согласование и физическую подготовку оборудования выполняют люди.
Демонстрация моделирует их решения заранее заданными значениями.

## Алгоритм 1: расчёт потребности

Вход: партия и список всех строк спецификаций.
Выход: список пар «идентификатор материала — необходимое количество» для выбранного изделия.

1. Проверить положительное целое количество изделий.
2. Перебрать все строки спецификаций.
3. Если строка относится к изделию партии, проверить положительность нормы.
4. Рассчитать `норма * количество изделий` и добавить результат.
5. Если для изделия нет строк, сообщить об ошибке; иначе вернуть результат.

Пусть n — число всех переданных строк спецификаций, k — число строк выбранного изделия (k <= n).
В худшем случае время O(n): цикл проходит n строк, каждая итерация содержит постоянное число действий.
Память результата O(k), дополнительная рабочая память без результата O(1).
При n=0 функция сразу сообщает об отсутствии спецификации; полная запись границы O(n+1).

## Алгоритм 2: проверка наличия материалов

Вход: список из k потребностей и список из m материалов.
Выход: общий признак готовности и отчёт по каждой потребности, включая дефицит.

1. Проверить, что потребности не пусты.
2. Для каждой потребности последовательно найти соответствующий материал в списке материалов.
3. Если материал отсутствует, добавить сообщение об отсутствии и установить отрицательную готовность.
4. Если найден, вычислить `max(0, потребность - доступное количество)`.
5. При положительном дефиците установить отрицательную готовность.
6. Вернуть все строки отчёта и итоговую готовность.

Худшее время O(k*m) при k,m >= 1: внешний цикл выполняется k раз, внутренний — до m раз.
Для допустимых данных такая граница также достигается: при k=m и совпадениях на разных позициях
общее число проверок равно 1+2+...+m = m(m+1)/2.
С учётом пустого списка материалов более полная оценка O(k*(m+1)+1).
Память результата O(k), рабочая память без результата O(1).
Здесь намеренно используется последовательный поиск. Если заменить его индексом-словарём,
изменятся и код, и оценка, и соответствующая блок-схема.
Оценки используют обычную модель постоянной стоимости арифметических операций и доступа
к фиксированному набору полей записи. В этих двух функциях нет поиска в словаре по переменному
набору идентификаторов, сортировки и копирования всего набора данных.

Оба алгоритма реализуют отдельные задачи BPMN; второй содержит ветвления и вложенный цикл.
Это версии для алгоритмического раздела КТ2. Блок-схемы следует строить именно по этим функциям,
включая проверки ошибочных входных данных.
Оценки относятся к указанным функциям, а не к полному запуску демонстрации.

## Подбор оборудования и принятые правила

Необходимые типы оборудования передаются параметром из технологического задания.
В демонстрации это ['Литьё', 'Сборка']. Их автоматическое получение из изделия не реализовано:
в текущей ER-модели нет сведений о требуемых типах оборудования для изделия.
Для подбора используется первое подходящее исправное оборудование в порядке входного списка.
Повторение типа в параметре означает необходимость ещё одной отдельной единицы того же типа.
Частичный подбор выводится как предложение, но при наличии недостающих типов не сохраняется.

Занятость вычисляется по назначениям других партий со статусами «Подготовка»,
«Готова к запуску», «Запущена». Статусы «Перенесена» и «Завершена» оборудование не блокируют.
При переносе текущие назначения партии снимаются; история назначений отдельными периодами не ведётся.
Планирования будущих интервалов и конкурентных пользователей в этой версии нет.

Перед фиксацией запуска повторно проверяются материалы, последний протокол контроля,
состояние и занятость назначенного оборудования. Последний отрицательный протокол блокирует запуск,
даже если раньше был положительный. Для одинакового времени протоколов используется больший id.
Повторный запуск запрещён. Даты-время в примере без часового пояса и должны быть в одном формате.
Остатки при фиксации запуска не списываются: отдельной операции выдачи/списания материалов в модели нет.
Одна проверка остатков не резервирует материалы для нескольких одновременно готовящихся партий.

## Ожидаемый вывод успешного сценария

```text
Партия П-0002: 1000 изделий
Полипропилен: нужно 2000, доступно 5000, дефицит 0 г
Игла: нужно 1000, доступно 1500, дефицит 0 шт.
Индивидуальная упаковка: нужно 1000, доступно 2000, дефицит 0 шт.
Подобрано оборудование: [1, 2]
Результат контроля: Соответствует
Итоговый статус: Запущена
```

shortage: дефицит полипропилена 1900 г, перенос с причиной «Нехватка материалов».
busy: установка литья занята другой партией, резервная на ремонте, перенос из-за оборудования.
quality_rejected: сотрудник задаёт отрицательный результат, сохраняются протокол и перенос.
У всех трёх отрицательных сценариев итоговый статус «Перенесена» и фактическая дата запуска null.
